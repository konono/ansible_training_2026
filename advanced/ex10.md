# 応用演習 10 - デバッグとベストプラクティス

[前に戻る](./ex9.md)

------

Ansibleのplaybookが期待通りに動作しないとき、効率的にデバッグする方法を知っていることは非常に重要です。この演習では、デバッグ出力の制御、Playbookデバッガの使い方、実行制御オプション、ansible-lintによる静的解析、そしてベストプラクティスについて学びます。

## Section 1: デバッグ出力の制御

```bash
$ mkdir ~/debug-lab
$ cd ~/debug-lab
```


### Step 2: verboseオプション（-v ～ -vvvv）

Ansibleは `-v` オプションの数に応じて出力の詳細度を変えることができます。

| オプション | 詳細度 | 出力内容 |
|-----------|--------|---------|
| `-v` | 基本 | タスクの結果の詳細 |
| `-vv` | 詳細 | タスクの入出力パラメータ |
| `-vvv` | 接続デバッグ | SSH接続の詳細、ファイル転送情報 |
| `-vvvv` | フルデバッグ | プラグインの動作、接続プラグインの詳細 |

まず確認用のPlaybookを作成します。

```bash
$ vi debug_test.yml
```

```yaml
---
- name: デバッグテスト
  hosts: node1
  gather_facts: false
  vars:
    app_name: myapp
    app_version: "1.0.0"
  tasks:
    - name: 変数を表示
      debug:
        msg: "{{ app_name }} v{{ app_version }}"

    - name: ファイルの存在を確認
      stat:
        path: /etc/hostname
      register: hostname_file

    - name: 結果を表示
      debug:
        var: hostname_file.stat.exists
```

各レベルで実行して違いを確認してみましょう。

```bash
# 通常の実行（verboseなし）
$ ansible-playbook debug_test.yml
```

```
TASK [変数を表示] *************************************************************************
ok: [node1] =>
    msg: myapp v1.0.0

TASK [ファイルの存在を確認] ***************************************************************
ok: [node1]

TASK [結果を表示] *************************************************************************
ok: [node1] =>
    hostname_file.stat.exists: true
```

```bash
# -v: タスク結果の詳細が表示される
$ ansible-playbook debug_test.yml -v
```

```
TASK [ファイルの存在を確認] ***************************************************************
ok: [node1] =>
    changed: false
    stat:
        exists: true
        path: /etc/hostname
        ...
```

```bash
# -vvv: SSH接続の詳細が表示される（接続トラブル時に有用）
$ ansible-playbook debug_test.yml -vvv
```

```
TASK [変数を表示] *************************************************************************
...
<node1> ESTABLISH SSH CONNECTION FOR USER: ansible
<node1> SSH: EXEC ssh -C -o ControlMaster=auto ...
...
```

### Step 3: debugモジュールの verbosity パラメータ

`debug` モジュールには `verbosity` パラメータがあり、指定したverboseレベル以上のときのみ出力されます。

```bash
$ vi debug_verbosity.yml
```

```yaml
---
- name: verbosityパラメータのデモ
  hosts: node1
  gather_facts: false
  vars:
    app_name: myapp
    app_config:
      db_host: localhost
      db_port: 5432
      db_name: mydb
  tasks:
    - name: 常に表示されるメッセージ
      debug:
        msg: "アプリ名: {{ app_name }}"

    - name: -vv 以上で表示される詳細情報
      debug:
        var: app_config
        verbosity: 2

    - name: -vvv 以上で表示されるデバッグ情報
      debug:
        msg: "Playbook: {{ ansible_play_name }}, Host: {{ inventory_hostname }}"
        verbosity: 3
```

```bash
# 通常実行 — 1番目のタスクのみ表示
$ ansible-playbook debug_verbosity.yml
```

```
TASK [常に表示されるメッセージ] ***********************************************************
ok: [node1] =>
    msg: 'アプリ名: myapp'

TASK [-vv 以上で表示される詳細情報] *******************************************************
skipping: [node1]

TASK [-vvv 以上で表示されるデバッグ情報] ***************************************************
skipping: [node1]
```

```bash
# -vv で実行 — 2番目のタスクまで表示
$ ansible-playbook debug_verbosity.yml -vv
```

```
TASK [常に表示されるメッセージ] ***********************************************************
ok: [node1] =>
    msg: 'アプリ名: myapp'

TASK [-vv 以上で表示される詳細情報] *******************************************************
ok: [node1] =>
    app_config:
        db_host: localhost
        db_name: mydb
        db_port: 5432
```

### Step 4: debug: var と debug: msg の使い分け

```yaml
  tasks:
    # var: 変数の中身をそのまま表示（型情報も確認できる）
    - name: varで変数を表示
      debug:
        var: app_config

    # msg: 文字列として整形して表示（複数の変数を組み合わせられる）
    - name: msgでメッセージを表示
      debug:
        msg: "DB接続先: {{ app_config.db_host }}:{{ app_config.db_port }}/{{ app_config.db_name }}"
```

---

**使い分けの指針**:
- **`var`**: 変数の構造を確認したいとき（辞書やリストの中身を確認）
- **`msg`**: 人間が読みやすい形式で情報を表示したいとき

## Section 2: Playbookデバッガ

### Step 1: debugger: on_failed — 失敗時にデバッガを起動

タスクが失敗したときにデバッガが起動するよう設定します。

```bash
$ vi debugger_demo.yml
```

```yaml
---
- name: デバッガのデモ
  hosts: node1
  gather_facts: false
  tasks:
    - name: 意図的に失敗するタスク
      command: /bin/false
      debugger: on_failed
```

```bash
$ ansible-playbook debugger_demo.yml
```

タスクが失敗すると、デバッガのプロンプトが表示されます。

```
TASK [意図的に失敗するタスク] *************************************************************
fatal: [node1]: FAILED! =>
    changed: true
    cmd:
    - /bin/false
    rc: 1
    ...
[node1] TASK: 意図的に失敗するタスク (debug)>
```

### Step 2: デバッガのコマンド一覧

デバッガのプロンプトでは以下のコマンドが使用できます。

| コマンド | 説明 |
|---------|------|
| `p task` | 現在のタスクの定義を表示 |
| `p task.args` | タスクの引数を表示 |
| `p result` | タスクの実行結果を表示 |
| `p vars` | 利用可能な全変数を表示 |
| `p vars['変数名']` | 特定の変数の値を表示 |
| `task.args['key'] = 'value'` | タスクの引数を変更 |
| `vars['key'] = 'value'` | 変数の値を変更 |
| `r` (redo) | タスクを再実行 |
| `c` (continue) | 次のタスクへ進む |
| `q` (quit) | Playbookの実行を中止 |

### Step 3: デバッガの実践的な使用例

失敗したタスクの原因を調査し、修正して再実行する例です。

```bash
$ vi debugger_fix.yml
```

```yaml
---
- name: デバッガで問題を修正する
  hosts: node1
  gather_facts: false
  vars:
    target_file: /tmp/nonexistent_dir/config.txt
  tasks:
    - name: ファイルにコンテンツを書き込む
      copy:
        content: "Hello World"
        dest: "{{ target_file }}"
      debugger: on_failed
```

```bash
$ ansible-playbook debugger_fix.yml
```

失敗した場合、デバッガで原因を調査します。

```
[node1] TASK: ファイルにコンテンツを書き込む (debug)> p task.args
{'content': 'Hello World', 'dest': '/tmp/nonexistent_dir/config.txt'}
[node1] TASK: ファイルにコンテンツを書き込む (debug)> task.args['dest'] = '/tmp/config.txt'
[node1] TASK: ファイルにコンテンツを書き込む (debug)> r
```

`r` で再実行すると、修正した引数でタスクが実行されます。

### Step 4: debugger: always — 全タスクをステップ実行

```yaml
---
- name: 全タスクをステップ実行
  hosts: node1
  gather_facts: false
  debugger: always
  tasks:
    - name: Step 1
      debug:
        msg: "ステップ 1"

    - name: Step 2
      debug:
        msg: "ステップ 2"
```

各タスクの実行後にデバッガが起動します。`c` で次のタスクに進みます。

```
TASK [Step 1] *****************************************************************************
ok: [node1] =>
    msg: ステップ 1
[node1] TASK: Step 1 (debug)> c

TASK [Step 2] *****************************************************************************
ok: [node1] =>
    msg: ステップ 2
[node1] TASK: Step 2 (debug)> c
```

## Section 3: 実行制御オプション

### Step 1: --start-at-task — 特定のタスクから実行を再開

長いPlaybookの途中から実行を再開したいときに使います。

```bash
$ vi long_playbook.yml
```

```yaml
---
- name: 長いPlaybook
  hosts: node1
  gather_facts: false
  tasks:
    - name: Step 1 - パッケージの確認
      debug:
        msg: "パッケージを確認中..."

    - name: Step 2 - 設定ファイルの配置
      debug:
        msg: "設定ファイルを配置中..."

    - name: Step 3 - サービスの起動
      debug:
        msg: "サービスを起動中..."

    - name: Step 4 - 動作確認
      debug:
        msg: "動作確認中..."
```

```bash
# Step 3 から実行を開始
$ ansible-playbook long_playbook.yml --start-at-task "Step 3 - サービスの起動"
```

```
TASK [Step 3 - サービスの起動] ************************************************************
ok: [node1] =>
    msg: サービスを起動中...

TASK [Step 4 - 動作確認] ******************************************************************
ok: [node1] =>
    msg: 動作確認中...
```

Step 1 と Step 2 はスキップされ、Step 3 から実行が開始されます。

### Step 2: --step — タスクごとに確認しながら実行

```bash
$ ansible-playbook long_playbook.yml --step
```

```
PLAY [長いPlaybook] ***********************************************************************
Perform task: TASK: Step 1 - パッケージの確認 (N)o/(y)es/(c)ontinue: y

TASK [Step 1 - パッケージの確認] **********************************************************
ok: [node1] =>
    msg: パッケージを確認中...
Perform task: TASK: Step 2 - 設定ファイルの配置 (N)o/(y)es/(c)ontinue: y
...
```

各タスクの実行前に確認が求められます。

- `y` (yes): タスクを実行
- `N` (No): タスクをスキップ
- `c` (continue): 以降のタスクを全て実行

### Step 3: --check --diff — ドライランと差分表示

`--check` は実際に変更を加えずに「何が変わるか」を確認するドライランモードです。`--diff` を併用すると、変更内容の差分が表示されます。

```bash
$ vi check_demo.yml
```

```yaml
---
- name: ドライランのデモ
  hosts: node1
  become: true
  gather_facts: false
  tasks:
    - name: ファイルを作成
      copy:
        content: |
          # Configuration file
          setting1=value1
          setting2=value2
        dest: /tmp/test_config.txt

    - name: ファイルの内容を変更
      copy:
        content: |
          # Configuration file
          setting1=new_value1
          setting2=value2
          setting3=value3
        dest: /tmp/test_config.txt
```

まず通常実行してファイルを作成します。

```bash
$ ansible-playbook check_demo.yml
```

次に内容を変更するPlaybookを `--check --diff` で実行します。

```bash
$ ansible-playbook check_demo.yml --check --diff
```

```
TASK [ファイルを作成] *********************************************************************
--- before: /tmp/test_config.txt
+++ after: /tmp/test_config.txt
@@ -1,4 +1,3 @@
 # Configuration file
-setting1=new_value1
+setting1=value1
 setting2=value2
-setting3=value3

changed: [node1]

TASK [ファイルの内容を変更] ***************************************************************
ok: [node1]
```

通常実行後のファイルは最終状態（`new_value1`）になっているため、`--check --diff` では1番目のタスクで「`new_value1` → `value1` への変更」として差分が表示されます。2番目のタスクは現在のファイル内容と同じため `ok` になります。`--check` なので実際にはファイルは変更されません。

### Step 4: タスクレベルの check_mode 制御

個々のタスクに `check_mode` を指定することで、`--check` の動作をタスク単位で制御できます。

```yaml
  tasks:
    - name: 常にチェックモードで実行（--check なしでもドライラン）
      copy:
        content: "test"
        dest: /tmp/always_check.txt
      check_mode: true

    - name: チェックモードを無視（--check 時でも実際に実行）
      command: date
      register: current_date
      check_mode: false
      changed_when: false

    - name: 日時を表示
      debug:
        var: current_date.stdout
```

---

**ポイント**:
- `check_mode: true` — `--check` なしで実行しても、そのタスクだけはドライランになる
- `check_mode: false` — `--check` 付きで実行しても、そのタスクだけは実際に実行される（情報収集タスクに有用）

## Section 4: ansible-lint

### Step 1: ansible-lint のインストール

```bash
$ pip install ansible-lint
```

### Step 2: 問題のあるPlaybookを作成

わざと問題のあるPlaybookを作成して、ansible-lint の検出機能を確認します。

```bash
$ vi bad_playbook.yml
```

```yaml
---
- hosts: node1
  become: yes
  tasks:
    - shell: cat /etc/hostname

    - yum:
        name: nginx
        state: present

    - name: restart nginx
      service:
        name: nginx
        state: restarted
```

### Step 3: ansible-lint の実行

```bash
$ ansible-lint bad_playbook.yml
```

```

Failed: 10 failure(s), 0 warning(s) in 1 files processed of 1 encountered. ...
```

### Step 4: 主要なルールの解説

| ルール | 説明 | 修正方法 |
|--------|------|---------|
| `fqcn[action-core]` | モジュール名にFQCN（完全修飾コレクション名）を使うべき | `shell` → `ansible.builtin.shell` |
| `name[missing]` | 全てのタスクに名前を付けるべき | `name:` を追加 |
| `name[play]` | Playにも名前を付けるべき | `name:` を追加 |
| `name[casing]` | タスク名は大文字で始めるべき | `restart nginx` → `Restart nginx` |
| `no-changed-when` | command/shell には `changed_when` を付けるべき | `changed_when: false` を追加 |
| `command-instead-of-shell` | シェル機能が不要なら `command` を使うべき | `shell` → `command` |
| `yaml[truthy]` | `yes`/`no` ではなく `true`/`false` を使うべき | `yes` → `true` |

### Step 5: 修正したPlaybook

```bash
$ vi good_playbook.yml
```

```yaml
---
- name: Nginx のセットアップ
  hosts: node1
  become: true
  tasks:

        state: restarted
```

```bash

```

```

```

### Step 6: .ansible-lint 設定ファイル

プロジェクト固有のルール設定を行うことができます。

```bash
$ vi .ansible-lint
```

```yaml
---
# 除外するルール
skip_list:
  - yaml[line-length]  # 行の長さ制限を無視

# 除外するパス
exclude_paths:
  - .cache/
  - tests/

# 有効にするプロファイル (min, basic, moderate, safety, shared, production)
profile: production

# 警告をエラーとして扱う
strict: true
```

### Step 7: CI/CDパイプラインでの使用

ansible-lint を CI/CD パイプラインに組み込むことで、マージ前にPlaybookの品質を自動チェックできます。

```yaml
# .github/workflows/lint.yml（GitHub Actions の例）
name: Ansible Lint
on: [push, pull_request]
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: ansible-lint を実行
        uses: ansible/ansible-lint@main
```

## Section 5: ベストプラクティスまとめ

### Step 1: ディレクトリレイアウト

推奨されるプロジェクト構成は以下の通りです。

```
project/
├── ansible.cfg              # Ansible設定
├── site.yml                 # メインPlaybook（エントリーポイント）
├── webservers.yml           # webサーバー用Playbook
├── dbservers.yml            # DBサーバー用Playbook
├── inventory/
│   ├── production.yml       # 本番インベントリ
│   └── staging.yml          # ステージングインベントリ
├── group_vars/
│   ├── all.yml              # 全ホスト共通変数
│   ├── web.yml              # webグループ変数
│   └── db.yml               # dbグループ変数
├── host_vars/
│   └── node1.yml            # ホスト固有変数
├── roles/
│   ├── common/              # 共通Role
│   ├── nginx/               # nginx Role
│   └── app/                 # アプリケーション Role
├── templates/               # Playbook用テンプレート
├── files/                   # Playbook用静的ファイル
└── .ansible-lint            # lint設定
```

`site.yml` はエントリーポイントとして、他のPlaybookをインポートします。

```yaml
# site.yml
---
- import_playbook: webservers.yml
- import_playbook: dbservers.yml
```

### Step 2: 命名規則

| 対象 | 規則 | 例 |
|------|------|-----|
| Role名 | 小文字、ハイフン区切り | `nginx-proxy`, `app-server` |
| 変数名 | 小文字、アンダースコア区切り | `http_port`, `app_version` |
| タスク名 | 動詞で始まる簡潔な説明 | `install nginx packages` |
| ファイル名 | 小文字、ハイフン区切り | `site.yml`, `web-servers.yml` |
| Roleの変数プレフィックス | Role名をプレフィックスにする | `nginx_port`, `nginx_config_path` |

### Step 3: 冪等性（idempotency）パターン

command/shell モジュールはデフォルトでは冪等ではありません。`creates` / `removes` パラメータを使って冪等性を確保します。

```yaml
  tasks:
    # 悪い例: 毎回実行される
    - name: アプリケーションをビルド（非冪等）
      ansible.builtin.command: make build
      args:
        chdir: /opt/app

    # 良い例: ファイルが存在しなければ実行
    - name: アプリケーションをビルド（冪等）
      ansible.builtin.command: make build
      args:
        chdir: /opt/app
        creates: /opt/app/build/app.bin

    # 良い例: changed_when で変更検知を制御
    - name: データベースのマイグレーション状態を確認
      ansible.builtin.command: python manage.py showmigrations --plan
      register: migration_status
      changed_when: false

    - name: マイグレーションを実行
      ansible.builtin.command: python manage.py migrate
      when: "'[ ]' in migration_status.stdout"
```

### Step 4: package モジュールによるポータビリティ

OS固有のパッケージマネージャ（`yum`, `apt`）ではなく、汎用的な `package` モジュールを使うことで、OSに依存しないPlaybookを書けます。

```yaml
  tasks:
    # 悪い例: RHEL/CentOS でしか動かない
    - name: nginx をインストール（yum）
      ansible.builtin.yum:
        name: nginx
        state: present

    # 良い例: どのOSでも動く
    - name: nginx をインストール（package）
      ansible.builtin.package:
        name: nginx
        state: present
```

ただし、パッケージ名がOSによって異なる場合は変数で吸収します。

```yaml
# group_vars/os_RedHat.yml
firewall_package: firewalld
```

### Step 5: その他のベストプラクティス

```yaml
  tasks:
    # ハンドラを使ってサービス再起動を効率化
    - name: nginx設定を配置
      ansible.builtin.template:
        src: nginx.conf.j2
        dest: /etc/nginx/nginx.conf
      notify: restart nginx

    # タグを使ってタスクをグループ化
    - name: パッケージをインストール
      ansible.builtin.package:
        name: nginx
        state: present
      tags:
        - install
        - nginx

    # failed_when で失敗条件をカスタマイズ
    - name: ヘルスチェック
      ansible.builtin.uri:
        url: "http://localhost/health"
        status_code: 200
      register: health_check
      failed_when: health_check.status != 200
      retries: 3
      delay: 5
```

```bash
# タグで実行対象を絞り込む
$ ansible-playbook site.yml --tags install
$ ansible-playbook site.yml --skip-tags nginx
```
